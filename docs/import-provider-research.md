# Import and catalog-provider research

Checked 2026-10-03. This is product research, not legal advice. “High” means confirmed in an accessible first-party page; “Medium” means the official page is linked but was not crawlable, or the implementation details need verification against a real export. Re-check terms/API docs before release.

## Decision summary

- Start with **user-owned file imports** for Letterboxd, IMDb, Goodreads, MyAnimeList (MAL, after validating a real official export), plus a documented generic CSV mapping flow. Parse locally where possible; preview all matches and field conversions; never scrape provider sites.
- Do not implement AniList API access for Tastellar’s tracker/list features absent written permission. Its current terms prohibit API use in “competing, non-complementary services of the same nature,” explicitly including anime/manga list or tracker services, and apply that restriction to user and media data. This is a direct conflict for a multi-media tracker even if the feature is read-only.
- Steam is possible only after resolving the developer-key and privacy requirements. Steam’s documented owned-games API can return an owned catalogue plus playtime, but games must be visible to the requester; it does not establish that a game was completed.
- For future opt-in account/API migration, Trakt is the clearest permitted candidate: its current policy explicitly permits managing a user's own history, ratings, lists, and a one-off personal migration, while prohibiting scraping and catalog/community mirroring.
- Metadata lookup should be source-specific, not a universal scraped aggregator. IGDB (games) and Open Library (books) are promising, subject to their distinct rules. TMDB is useful for films/TV but explicitly free only for non-commercial projects with attribution. Since the app may accept Boosty contributions, do not assume it qualifies as non-commercial; obtain written provider clearance before enabling TMDB. No API license automatically grants copyright in cover art.

## Field mapping / import semantics

Persist provider identifiers separately from the app's own media identity (recommended relation: `(provider, provider_media_type, external_id, canonical_media_id, source_url, observed_at)`, unique on provider/type/external ID). A title/year match is only a proposal; show candidates and require user confirmation for ambiguous matches. Preserve raw source row/fields long enough to explain conversions and allow a preview, then retain only the fields the user elected to import.

Suggested normalized states: `planned`, `current`, `completed`, `paused`, `dropped`, plus `owned` as a separate collection attribute. Avoid forcing “owned” into the viewing/reading lifecycle. Keep rating as `(value, source_scale, source_provider)` or convert while retaining original value/scale. Keep start, finish, and activity/viewing events separately; a single date field loses Letterboxd rewatches and histories such as Trakt.

## Provider-specific findings and source evidence

### Letterboxd — file import recommended (high confidence)

The official [import format](https://letterboxd.com/about/importing-data/) accepts its own UTF-8 CSV and IMDb CSV. Its accepted import headers are distinct from native export schemas: they include `LetterboxdURI`, `tmdbID`, `imdbID`, `Title`, `Year`, `Directors`, `Rating` (0.5–5 by half-stars), `Rating10` (1–10), `WatchedDate` (`YYYY-MM-DD`), `Rewatch`, `Tags`, and `Review`. ID/URI matching is exact; title matching is best-guess. The importer previews matches, has a 1 MB limit, marks imported profile films watched, and combines duplicate film/date rows.

Header-only inspection of one test account's [official export bundle](https://letterboxd.com/user/exportdata/) found these fields: `watched.csv` and `watchlist.csv` have `Date, Name, Year, Letterboxd URI`; `ratings.csv` adds `Rating`; `diary.csv` adds `Rating, Rewatch, Tags, Watched Date`; `reviews.csv` adds `Review`. The bundle also includes likes/comments and deleted/orphaned CSVs. No profile or media row values were inspected. The tested native schemas contain Letterboxd URI but no IMDb/TMDB IDs. Preserve `Date` and `Watched Date` as distinct source columns; the header alone does not establish their semantics. This evidence covers one account/export version, not every user's export. Do not extract hidden IDs or scrape for crosswalks. Letterboxd says API access is by request and its [API policy](https://letterboxd.com/api-beta/access/) is restrictive for private/personal projects and data-analysis/recommendation uses; use the user's export rather than depending on API approval. Do not copy catalog artwork into Tastellar without separate rights.

### IMDb — user CSV for personal ratings only (high confidence)

IMDb's [Ratings FAQ](https://help.imdb.com/article/imdb/track-movies-tv/ratings-faq/G67Y87TFYYP6TWAV) confirms users can export their ratings history as CSV and that their individual rating is 1–10, one rating per title. IMDb also documents CSV export for [check-ins](https://help.imdb.com/article/imdb/track-movies-tv/check-ins-faq/GG59ELYW45FMC7J3); Letterboxd's [migration guide](https://letterboxd.com/about/migrating-from-imdb/) documents supported exports of ratings, check-ins, watchlists and lists, but says IMDb review exports are unavailable. Exact CSV headers should be validated on representative user files; do not equate rating date with watch date.

IMDb's [software-use FAQ](https://help.imdb.com/article/imdb/general-information/can-i-use-imdb-data-in-my-software/G5JTRESSHJBBHTGX) limits its datasets to personal/non-commercial use, disallows scraping, and disallows republishing/repurposing datasets into a movie-information database. The datasets are therefore not a safe public Tastellar catalog source. IMDb offers [separate licensing](https://help.imdb.com/article/imdb/general-information/content-licensing/GZGA5HDQ8NE97LVR). Importing a file exported by the user from their own account is a different, narrower use; do not turn uploaded rows into shared catalog data.

### Goodreads — user library CSV only (high confidence for terms/export route; medium for exact headers)

Goodreads support documents [CSV library import/export](https://help.goodreads.com/s/article/How-do-I-import-or-export-my-books-1553870934590) (its older official support answer also describes exporting a library CSV). User list fields commonly include title/author, Goodreads book ID, ISBN/ISBN-13, user's rating, shelves, date read, date added, review, read count and private notes; exact columns vary and must be discovered from the uploaded header instead of assumed. Map exclusive shelves, not Goodreads' aggregate score. Preserve book-work and edition identity distinctly when ISBNs exist.

The current [Goodreads Terms](https://www.goodreads.com/about/terms?id=188) prohibit “any collection and use of any book listings, descriptions, reviews” and data-mining/robots. This rules out scraping or constructing a shared metadata/catalog service from Goodreads. No crawlable first-party public API onboarding suitable for a new app was found; do not rely on historical or third-party claims about keys or APIs. A user-initiated personal CSV export/import is the practical route; keep imported user activity scoped to that user's account.

### MAL and AniList — anime/manga user-list import (MAL conditional; AniList API gated)

MAL's official [API v2 reference](https://myanimelist.net/apiconfig/references/api/v2) and [OAuth guide](https://myanimelist.net/apiconfig/references/authorization) are the authority for implementation, but were inaccessible during review. Commonly documented API fields include list status, score, start/finish, watched episodes/read chapters, read volumes, comments/tags, priority and rewatch state; treat this as a field checklist, **not verified current response schema**. MAL list-status semantics are anime `watching/completed/on_hold/dropped/plan_to_watch`, manga `reading/completed/on_hold/dropped/plan_to_read`. Before enabling, manually verify OAuth registration/consent, exact field names, status enums, user export flow, rate limit, storage/cache policy and developer agreement from current MAL docs. Prefer a documented official user export if one is currently offered; absent that, do not advertise XML/CSV export support until the user provides a sample obtained from the official UI and it is validated. Don't scrape pages or route through an unofficial API.

AniList API field shape is confirmed by its [MediaList reference](https://docs.anilist.co/reference/object/medialist) and [status enum](https://docs.anilist.co/reference/enum/medialiststatus): score, episode/chapter and volume progress, repeat count, privacy, notes/custom lists, start/complete dates, plus `CURRENT`, `PLANNING`, `COMPLETED`, `DROPPED`, `PAUSED`, `REPEATING`. The Terms page states: “Use of the AniList API within competing, non-complementary services of the same nature is prohibited.” It explicitly includes anime/manga list/tracker services and applies to user as well as media data. This appears to bar both catalog search and account-list OAuth in Tastellar's current tracker context. AniList OAuth also has no scopes and tokens grant “almost” full user-data access, per [auth docs](https://docs.anilist.co/guide/auth/), so it is unusually broad. **Gate:** no AniList API until written clearance or confirmed product/terms change. A user's independently obtained official personal export file could be a distinct path, but no current official AniList CSV/JSON export specification was available for verification; accept neither guessed nor scraper-generated export formats. Offer generic CSV/manual import as fallback and preserve any user-provided AniList/MAL IDs as opaque external IDs, without querying AniList.

### Steam — conditional account API (high confidence)

The official [IPlayerService docs](https://partner.steamgames.com/doc/webapi/IPlayerService?l=english&language=english) expose `GetOwnedGames`, `GetRecentlyPlayedGames`, and playtime endpoints. Owned-game results are available only if the user's owned-games/game-details are visible; `include_appinfo` adds name/icon and free games are excluded unless requested. Store `appid`; distinguish owned, playtime and recently played from a user's own completion judgment.

The [Steam Web API Terms](https://steamcommunity.com/dev/apiterms) require a privacy policy covering non-public end-user Steam data and where stored, retrieval only on end-user request, a confidential non-shared API key, no intercepting/storing Steam passwords, and no implication of Valve affiliation. Because the developer Web API key cannot be embedded in an open-source client, use a controlled backend only with a compliant privacy story and security review; otherwise defer API connection. Never ask users for Steam credentials or distribute the app key. Verify current key registration and any applicable endpoint restrictions before launch.

### Trakt — best extra import/API candidate for film + TV (high confidence)

Trakt's current [API Use Policy](https://developer.trakt.tv/docs/api-use-policy) explicitly allows apps to manage a user's own watch history, ratings and lists and even a one-off script migrating that user's history. It prohibits scraping, bulk harvesting, mirroring its catalog/community data, reselling/redistribution, or using replacement credentials to evade a blocked integration. The official [API intro](https://developer.trakt.tv/) distinguishes history, watched dates/repeats, watchlists, lists and favorites; [app registration](https://developer.trakt.tv/docs/create-an-app) requires a verified GitHub account and branding/policy compliance. This is a strong later OAuth connector, with user authorization and activity-only synchronization; keep Trakt IDs and any cross-provider IDs separately. Do not mirror its catalog.

## Catalog search and artwork options

The safe product shape is a user-initiated lookup that returns a small candidate list (title, year, provider, external ID, permitted image URL); user selects a result, and Tastellar stores its own record plus provenance. Avoid a background bulk catalogue, permanent local cover archive, or scraping HTML. Provider API access, database rights, and artwork copyright are separate permissions; a provider returning an image URL is not a blanket image license.

## Rights, donations, and practical safeguards

Open-source licensing covers Tastellar code, not other services' structured databases, user reviews, logos, or cover art. Facts may receive different copyright treatment than original database selection/arrangement, and many countries also protect database investments and contractually restrict API use. For the Russian-law context, see [Civil Code Article 1260 (compiler works)](https://www.wto.org/english/thewto_e/acc_e/rus_e/wtaccrus58_leg_360.pdf) and [Article 1334 (database producer rights)](https://www.wto.org/english/thewto_e/acc_e/rus_e/wtaccrus54_leg_1.pdf); this is not a jurisdiction-by-jurisdiction legal opinion.

Do **not** state or rely on “free/open source means noncommercial.” TMDB's written definition is revenue-oriented; IGDB routes commercial projects to partnership; Comic Vine and Goodreads exclude commercial use; AniList's competitor restriction is independent of the noncommercial/free threshold. No authoritative ruling was found that voluntary Boosty support is exempt. Whether donations count depends on the API contract and facts (e.g. who receives funds, whether they support operating expenses, how promoted); that is an unresolved legal/provider classification, not a conclusion. Before using a non-commercial-only catalog API, disclose the app and Boosty arrangement to the provider and get written confirmation or choose a different source. Consult qualified counsel for tax and jurisdiction-specific obligations.

Recommended controls:

1. Track rights/provenance per imported/enriched field and image (provider, ID, URL, fetched date, applicable terms/version, attribution requirement); implement deletion/refresh and takedown paths.
2. Keep user-imported activity private by default; upload only at the user's request, never merge private rows or notes into a shared catalog; document retention and deletion.
3. Save external IDs across providers with namespaces; use an explicit crosswalk only when it is actually supplied by a permitted source. IDs help reconciliation but do not grant license to copy that provider's metadata/artwork.
4. At import preview, show detected source, counts, matched/unmatched/ambiguous rows, status/rating/date mapping, duplicate policy and exactly which optional reviews/tags/notes will be retained. Let users choose overwrite/skip/merge and confirm before commit. Record partial date precision, don't invent missing dates, and allow re-import idempotently by external ID.
5. Use no scraping, browser automation, unofficial user-data endpoints, or third-party converter that harvests private accounts. Support user-export files and documented official APIs only.

## Evidence confidence and remaining checks

- **High:** Letterboxd import/export docs and fields; IMDb ratings export/rating scale and dataset restrictions; Goodreads terms; AniList terms, OAuth and list fields; Steam API and terms; Trakt API policy; TMDB commercial/attribution rule; IGDB official stated use/caching rules; Open Library search/cover rules; Comic Vine API rules; Google Books official search/reference docs.
- **High for one observed bundle; medium for generalization:** Letterboxd native export CSV headers were inspected in one test account/export, without reading account/media rows. Confirm consistency against future export versions/users; native date-column semantics still need a careful mapping decision. Other medium-confidence items: Goodreads exact export headers; IMDb exact CSV columns for each export subtype; whether MAL currently offers an official personal export and exact current API field/permission details (official references linked above were inaccessible to this crawler); the operational impact of Steam WebAPI key registration and public-app privacy/storage design; detailed Google Books image/response retention terms as applied to Tastellar's exact UI.
- **Unresolved permission gates:** written AniList clearance; MAL's current developer terms and export validation; Steam implementation/key/security and privacy; TMDB/IGDB/Comic Vine treatment of voluntary Boosty support; all third-party artwork rights. Revisit these gates before implementing the corresponding connector/search provider.
