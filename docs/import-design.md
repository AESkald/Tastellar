# User library import and catalog search design

**Status:** the current implementation is summarized below. The original product proposal and provider-rights notes are retained afterward for context.

## Import and catalog revision (October 2026)

- Import defaults to no batch tags; mapping or creating tags remains an explicit opt-in. Historical exports with known omitted Home settings remain restorable with their original checksum semantics.
- IMDb genre `Animation` takes precedence over movie/series classification and maps to the existing Animation type (`anime` internally).
- New manual entries and imports without a recognizable source status start as already experienced. The import category step offers a whole-batch status override; explicit planned/dropped choices do not import a native overall score. Source ratings remain in import history.
- Catalog selection enables cover downloading by default. Provider references are metadata for trusted downloads into the same local asset store used by manually uploaded covers. Original cover bytes belong in portable backups and recap rendering.
- Batch enrichment lets the user choose one catalog, stages its first result for each canonical work, starts at most one lookup per second, reports progress, and supports stopping. These choices remain reviewable before commit; individual lookup is available for corrections.
- Search uses one selected catalog, capped at eight results per page. The last selected catalog is remembered; no all-catalog option is exposed. Queries and result lists survive switching between catalog and manual editor tabs.
- Selection mode exposes batch type/status edits, cover removal, and trash actions in the right sidebar. Native batch changes validate the current revision and commit atomically. Planned/dropped changes clear overall scores and invalidate affected ranking placements; criterion scores remain.
- Poster frames use 2:3 in library, details, ranking, and recap. Higher-resolution official IGDB cover variants replace thumbnail requests; an already low-resolution original cannot acquire detail through resizing.
- External identifiers and provider provenance stay in internal metadata, outside the media details sidebar. Required TMDB branding belongs in Settings/About credits. The import wizard has no Provider terms control. Review match opens a separate modal with its own accessible title and selected-cover summary.

### Enrichment conflicts and cover failures

A selected catalog identity already belonging to a unique existing work produces a visible reuse proposal before commit. Existing ratings, reviews, status and local covers remain unless the user explicitly changes them. Shared catalog identities within the batch are surfaced for review rather than silently merging fuzzy title matches. Explicit separate-work choices omit conflicting catalog identities; native source-identity uniqueness remains protected.

An unavailable cover does not cancel the media import. The receipt identifies the affected work and offers Retry or Skip cover. Failed downloads never masquerade as saved remote-reference covers. Cover retries update only local cover bytes and the matching import after-snapshot atomically, so Undo still works while genuine later edits remain protected. Existing local covers are preserved without redundant downloads; legacy remote-only covers remain eligible for migration.

### App-owned provider configuration

The desktop build contains no provider credentials and does not read `.runtime/provider-credentials.json` or `TASTELLAR_PROVIDER_CREDENTIALS_FILE`. Users enter keys in API settings. The native app stores them in its local SQLite `provider_credential` table, updates its active provider session after each successful save or clear, and exposes only configured status to the interface. Keys are not logged. Portable version 4 archives include configured keys as plain text; treat exports as sensitive. Restoring versions 1–3 clears existing provider keys.

Embedding a credential in a distributed desktop application makes it extractable. This arrangement does not make IGDB client secrets private; a future hosted proxy with quotas is needed to protect shared secrets and enforce a global request budget. The batch lookup throttle is per running client, not a global limit across installations. Google Books API keys should be restricted to the Books API; API keys are distinct from OAuth authorization to private Google Drive files. Image lookup uses provider cover APIs rather than scraping arbitrary Google Images results.

## Recommendation

Build one additive, reviewable import session that stages all selected files/sources together before matching or writing. Keep the portable archive restore as a separate Replace operation. The current desktop parser accepts Letterboxd ZIP, IMDb CSV, Goodreads CSV, MyAnimeList XML/XML.gz, one-title-per-line TXT and supported CSV/TSV, generic CSV/TSV with recognized columns, and a conditional, explicit Steam owned-games API request. Steam requires the user's API key and a profile with game-details visibility; no live Steam request was verified in this implementation because no test key was available. Generic CSV currently uses header aliases; it does not provide an arbitrary column-mapping step. MAL access is user-supplied files only; pasting a profile URL does not trigger acquisition, and there is no account-page scraping. The browser adapter is preview-only; committing requires the native desktop backend. There is no AniList connector. Steam's documented user APIs do not provide user wishlist/cart contents. User-selected media category and tag handling are required for every import, with source-based defaults and row-level overrides.

Preserve every provider's original score and provenance. Never use IMDb's aggregate `IMDb Rating` as the user's score, average conflicting ratings, overwrite local ratings by source order, or change criteria/ranking. For one personal score or multiple scores that normalize identically, preselect a visible `overallRating` proposal with calculation and source count; the user can accept or uncheck it. If new-item source scores conflict, leave the native score empty until a batch policy or row choice resolves them. Keep existing local scores by default. Catalog search is separate, explicit, and terms-gated; selection and cover use require field-by-field preview. No password collection, browser automation, scraping, or silent background syncing.

Enable each connector independently only when current terms, credentials, and the intended use permit it. AniList is outside current scope and is not offered. Goodreads stays export-file-only. MAL direct HTML acquisition is also outside the current flow; accept a user-supplied native XML/XML.gz or supported CSV/TSV file. Provider keys are persisted in native SQLite, never browser storage, and never returned to the UI; the current portable archive intentionally includes them in plain text. For any source/image with unclear rights, allow the list data to import while omitting catalog enrichment and covers; none of the inspected exports contain covers, and a missing cover never blocks import.

## Current Tastellar model and constraints

The TypeScript and Rust `Entry` DTOs store one optional `mediaTypeId`, `title`, `disposition` (`experienced | planned | dropped`), optional integer `overallRating` from 1–10, local `coverAssetId`, partial `releaseDate`, `reviewText`, criterion ratings, tag IDs, namespaced external identities, and an optional attributed remote-cover reference. A native rating still requires `experienced`. Source-specific ratings, source dates/status, progress, tags, and repeat/diary activities are preserved as import provenance; they are not flattened into a new in-progress/paused lifecycle or canonical progress model. There is no separate format/edition relation yet. The current code keeps those source semantics available without treating ownership, a rating, or playtime as completion.

SQLite persists these entries in `entry`; media type remains a single foreign key. Imports stage in a versioned session, commit additively in one transaction, attach source identities/provenance, and record an undoable import batch. Undo refuses if a later change conflicts with the saved import snapshot. User-created covers remain validated local PNG/JPEG/WebP assets, bounded to 25 MB and 40 megapixels. Catalog search can additionally persist an explicitly selected provider-hosted cover reference when its adapter supports that mode; image bytes are not copied into backups. See [`crates/storage/src/lib.rs`](../crates/storage/src/lib.rs), [`crates/storage/src/import.rs`](../crates/storage/src/import.rs), and [`LibraryEntryEditor.tsx`](../apps/tastellar/src/features/library/LibraryEntryEditor.tsx).

The seeded media-type IDs are `tv-series`, `films`, `anime` (display name “Animation”), `comic`, `games`, and `literature`. “Animation” is an overlapping user-facing category: an animated film can also be a film, and an anime series can also be a series. Keep source-native format (anime, manga, film, series, game, book/edition, etc.) separate from this primary user-selected bucket. Do not replace the user's category based on a provider guess. Entries now store namespaced external identities and an attributed remote-cover reference; import rows retain source-specific scores, dates, progress, status, and activities in provenance. No canonical in-progress/paused lifecycle or format/edition relationship has been added yet.

Current archive restore in [`projectstructure/architecture/12-data-safety.md`](../projectstructure/architecture/12-data-safety.md) is a validated full Replace with a pre-import recovery archive and one transaction. It has no preview or merge. The new list importer should not overload that restore flow.

## User experience

### Import a personal list

Add **Import from another service…** beside the existing Library import/export action. Start a new import session and let the user add several files/providers before review. The current file choices are Letterboxd ZIP, IMDb CSV, Goodreads CSV, MyAnimeList XML/XML.gz or supported CSV/TSV, and generic CSV/TSV. Steam is an official-API source configured with the user's saved Web API key and a user-supplied SteamID/profile URL. Each provider card states what will be parsed and what is ignored. File parsing and matching work offline; catalog and Steam requests need network access. Never request a provider password or automate login; never log credential values. Provider keys live in local SQLite and appear as plain text in portable version 4 archives when configured, so exported archives must be kept private.

Parse every selected source into one temporary local staging area before building a single cross-source match plan. Do not commit each provider serially: this allows Tastellar to see cross-source duplicates and rating disagreements before either source is attached to the library. The screen shows row/work counts per file and in total, ready/skipped rows with reasons, within- and cross-source matches, conflicts, missing metadata, and every field that could replace an existing value. Keep the original source label on each staged value. Allow adding/removing sources and reparsing before commit.

Make **Target media category** and **Tags** required visible review steps on every import. Prefill a source-based suggestion but require the user to accept or change it: Letterboxd suggests Films; Goodreads suggests Literature; MAL anime suggests Animation and manga suggests Comics; IMDb `Title Type` suggests Films for Movie and TV series for TV Series, while Animation remains selectable; generic CSV asks. Let the user pick one category for a source group, set batch defaults per provider/group, override per row, or split a mixed import by detected media kind. Use current IDs under the user's control; do not silently change an existing work's category. The tag step requires an explicit choice of “No tags,” map selected source tags/shelves to existing tags, or create selected new tags. Do not create tags from shelves/genres automatically. Save source/group defaults and allow per-row overrides; show exact existing/new tag names before commit.

Review text and source tags/shelves remain off by default. Provide clear controls for status, progress, original ratings, local Tastellar ratings, tags, and covers. The provider's original score stays in source provenance regardless of the local score choice. The default local-score policy is keep an existing Tastellar score; for new works preselect a single-source or equal-normalized score proposal in the final batch preview, where the user may accept or deselect it. No source order is a resolution rule.

Resolve an exact namespaced `(provider, provider item ID, entity kind)` match automatically and reversibly, with a clear link in the preview. A verified crosswalk from a permitted selected catalog can auto-group an exact item too, provided media kind/edition semantics agree. Still flag semantic contradictions (for example, book edition vs audiovisual work or a Film vs TV Series choice) for review. Use confidence buckets for other matches: high-confidence title/original-title plus compatible format/year/author/creator candidates are preselected suggestions the user can accept in bulk after checking a short sample; medium/low confidence candidates require row review. Every match remains editable before one atomic commit. Upload order is never precedence. Cross-provider matches need an ID crosswalk in the selected file or permitted catalog result; never scrape a hidden crosswalk. Display source names, original titles, years, format/category, IDs, and edition/season clues. The user can choose “Link to existing,” “Create separate work,” or “Skip,” in bulk or by row. Same-title adaptations must remain separate even when strings match. Different book editions, seasons, volumes, issues, and game editions also remain separate until identity is clear. Never collapse distinct source activity events merely because the work identity matches.

The actual files show why this matters: 28 source works across the three exports include six Letterboxd/IMDb same-film candidates found by title/original title, even though Letterboxd provides no IMDb/TMDb cross IDs. If a user confirms all six links, the batch contains 22 canonical works; before confirmation show all 28 rows and every candidate. Some source `Year` values differ from the same row's `Release Date` by a year, so release-date mismatch is not decisive identity evidence. The fixture also contains a same-franchise anime/light-novel pair that must stay separate. Use these as collision-preview cases, not automatic merges. The fixture has no conflicting personal ratings: IMDb `Your Rating` is blank for all rows.

For ratings, show each source's original value, scale, normalization method, and whether the source timestamp is comparable. For one personal source score, or multiple scores that normalize identically, preselect the native-score proposal for compatible entries and show its source count/calculation (e.g. Letterboxd 4.5/5→9/10; Goodreads 4/5→8/10; personal IMDb 7/10→7/10). The user can uncheck or override; don't require a per-row prompt when the proposal is unambiguous. The inspected IMDb file's `Your Rating` is blank in all 10 rows; populated `IMDb Rating` is an aggregate and must never become a personal score. The Goodreads file has three user 4s, four 5s, and one 0; treat zero as unrated. For genuine incoming conflicts, keep all original ratings in provenance and ask for one batch policy: prefer a named provider (user-visible, reorderable priority list not tied to file order), use latest only when source timestamps mean the same thing and are actually comparable, manual choose per work, or preserve source-only/no native rating. Keep row override in all modes. Do not average automatically. `Date Added`, Letterboxd `Date`/`Watched Date`, and watch/finish dates are not rating timestamps. Existing native local ratings win by default; explicit overwrite policy requires showing old/new and saving the old value for Undo. No actual personal-rating conflict was present in the supplied fixture; conflict scenarios belong in synthetic adversarial copies.

Before commit, show a concise global plan: new works, auto-linked exact-ID works, bulk-accepted high-confidence candidates, row-review candidates, skipped rows, category/tag mappings, rating decisions, and each existing value that will change. Existing field default is **fill blanks only**. No write follows uploaded file order. An accepted native rating changes the score only; it doesn't change activity state, criteria, or ranking position. Where the legacy score/experience invariant blocks a source rating, preserve the source rating and explain why native mapping awaits the lifecycle/ranking schema change. New rank-eligible scored works remain unplaced. Require explicit opt-in to copy user-authored source reviews. Never import provider editorial descriptions, critic text, or other users' reviews as metadata.

Commit the entire session once after review; imported files remain local and can be discarded before commit. If optional enrichment fails, let the user commit the imported list without enrichment. Then show a receipt with all providers/files, mappings, counts, skipped-row reasons, unresolved items, and Undo. Import is additive and does not change criterion scores or ranking placement. A new item with an accepted Tastellar score remains unplaced until the user explicitly places it; if score import is off, don't invent a score or mark an item completed solely to satisfy the existing score rule.

### Search a catalog while adding a work

In the existing Add work editor, provide **Search catalogs** as an explicit action separate from manual entry. Search only selected, enabled catalog providers and disclose that the query is sent to that provider. Search begins with the title and the chosen media category; allow source, year, and media-type filters. Search pages are debounced, stale responses discarded, and repeated provider/entity IDs removed. An optional import-batch lookup can use IMDb title IDs or Goodreads ISBNs against exact-ID endpoints; these results remain per-row suggestions and require explicit selection. Results show title, original title where useful, year, native format, creator, provider, source link, and a cover preview when available. The UI keeps Steam out of catalog search; Steam is an import source only. The adapter determines whether a provider cover may be persisted by reference; public release still requires current provider-terms and revenue-classification review.

On selection, open a field review, not an immediate save. Pre-fill only empty fields by default. Let the user accept or edit title, year/date, source IDs, format and cover independently. Show image attribution/licence terms where required. If a provider's image terms don't allow persistent reuse, show a transient result preview only and keep the local cover unset; provide the existing local upload option. Search failure, rate limits, or no cover must leave manual entry fully usable.

Search providers must be configured through a capability/terms registry, not a hard-coded blanket assumption that a public endpoint is reusable. Disable a provider when credentials, regional availability, API terms, attribution, or caching permission are missing or change. Search queries should not include the user's private list or rating unless a specific feature requires it and the user separately agrees.

## Field and status mapping

Treat the existing `disposition` as a compatibility/ranking bucket, not a complete source-status vocabulary. Add normalized lifecycle status and progress separately for in-progress/on-hold states and activity history. Preserve exact source status and progress unit. Do not silently map watching/reading/on-hold to planned or infer completion from ratings/playtime. Existing `experienced` records do not prove 100% completion; leave new activity state unspecified on migration unless the user confirms it. A source's explicit completed status may map to completed; a rating alone does not imply completion or experienced.

Review the storage invariant that currently requires a non-null `overallRating` to have `disposition='experienced'`. The target schema should keep lifecycle status, the user's numeric assessment, and ranking eligibility separate: allow an explicitly accepted rating on in-progress/on-hold/dropped works without making them completed/experienced or placing them in the canonical ranking. An explicit completed source status may map to experienced when the user accepts it, but a source score never sets completion. Until this schema/UI change exists, preserve incompatible scores in provider provenance and explain why the native score field stays empty; never fake experienced to bypass validation.

### Validated Letterboxd ZIP pattern

Header-only inspection of one user-requested export confirmed these files and row counts: `watched.csv` (2), `ratings.csv` (1), `diary.csv` (2), `watchlist.csv` (8), `reviews.csv` (0), and `comments.csv` (0). The inspected media files expose `Letterboxd URI` as the sole identity field; no IMDb/TMDb cross IDs were present. Exact schemas can vary by export version/account, so discover headers rather than assume them. Do not read/import `profile.csv` for media matching; it is unnecessary for this flow and contains profile/PII. Skip deleted/orphaned/likes/comments files unless a future user-facing import option explicitly supports them.

Build one local film row per canonical Letterboxd URI by joining the watched, ratings, and diary tables. Keep an origin marker per field so `Rating` in `ratings.csv` and `Rating` in `diary.csv` can be compared and conflicts reviewed rather than duplicated. Keep the watchlist relation separate: the same film can be watched and remain on a watchlist; expose that combination in preview instead of replacing one status with another. Each diary row becomes a separate activity event. Add a source-event table or equivalent with a unique source event key; form the key from provider, URI, the best validated event-date field, rewatch marker, and an occurrence ordinal among otherwise identical rows. Keep rating/tags as mutable event attributes rather than event identity. If a watched-date field is absent or blank, retain the raw row date but mark its semantics unknown. Never use only `(URI, Watched Date)` as a uniqueness key, because that would erase same-day repeats. `Date` and `Watched Date` are not interchangeable: in the inspected export all files' `Date` values were 2026-10-04 while diary `Watched Date` values were 2026-10-03, and the `Date` field's meaning remains unresolved. Preserve `Date` as opaque provenance until official documentation establishes its semantics.

Source ratings should be represented as `{value, scaleMin, scaleMax, format, sourceUpdatedAt}` and an explicit conversion record when copied to `overallRating` (algorithm/version and resulting integer). Detect and preserve the provider's scale; never guess an unknown or nonnumeric scale. Keep the raw value for re-import and audit. Current Tastellar supports integer 1–10 only.

Keep native work format and length separate from the six user-facing media buckets. A useful optional metadata shape is `{formatCode, lengthValue, lengthUnit, lengthScope}`, where scope distinguishes whole work, per episode, issue, or volume. Thus “TV series, animated” can remain one user category while retaining series format, animation trait, episode count, and per-episode runtime; manga retains chapter/volume progress separately from a book's page count. Don't convert episodes/volumes into minutes or infer total runtime from missing episode data. Store the selected normalized value plus source/provider identity and keep conflicting provider lengths in source provenance until the user chooses one.

Map a source release year to `releaseDate` with `precision='year'`; do not invent month/day. Source start/finish/watch dates are activity dates and must not be written as releaseDate, `createdAt`, or `updatedAt`. Provider lists/shelves/genres must not become Tastellar tags without a mapping preview; this agrees with [`projectstructure/specifications/07-library.md`](../projectstructure/specifications/07-library.md).

## Persistence proposal

Add normalized persistence through a deliberate schema migration; keep source identity/progress out of ad-hoc title suffixes and don't overload `reviewText` or tags.

1. **`external_identity`**: local `entry_id`, canonical `provider_key`, `external_id`, `entity_kind` (work, edition, season, volume, issue, game/app, etc.), optional canonical source URL, link date, and optional `parent_external_id`/relationship kind. Enforce uniqueness on `(provider_key, entity_kind, external_id)` so one source entity cannot silently attach to two works; allow multiple identities on one Tastellar entry. Reconcile explicitly when the same source has both work and edition IDs. IDs are matching evidence; they never auto-merge separate entries by title. For Letterboxd's validated native export, use its canonical URI as the cross-file identity; don't infer TMDb/IMDb identities from the import template or a title lookup.
2. **`entry_source_state`**: entry/identity relation, provider schema version, last imported time, native status, raw rating and scale, native progress counters/units, repeat count, source dates, and only those user-list fields necessary for supported re-import. Use validated typed columns for shared statuses and bounded versioned JSON for provider-specific extras. Store no full export row or full API response by default; omit descriptions and review bodies. Offer optional local, encrypted, redacted per-source payload retention only when needed for re-import/debugging and allowed by that provider's terms. Exclude credentials/tokens from these payloads and all logs; provide a visible retention period and delete-by-provider action.
3. **`external_activity_event`**: optional per-entry provider event identity, source event key, event kind, source date with explicit precision/semantics, rewatch flag/count or progress snapshot, and selected non-text attributes. Enforce `(provider, source_event_key)` uniqueness for idempotent re-import; do not collapse distinct same-day events. Store user review bodies only by separate explicit opt-in.
4. **`import_batch` and reversible changes**: provider, acquisition kind (export/API/catalog), parser/mapping version, completion time, counts, selected mapping options, and reversible per-entry field deltas. Do not retain uploaded export files after preview/commit. Undo only if affected records still match their post-import versions; otherwise report a conflict and leave later edits intact. Deleting import history should detach provenance/identities only after the UI previews the effect; it must never unexpectedly delete works.
5. **`activity_status` / `progress`**: optional normalized lifecycle state plus counts/unit, separate from legacy `disposition`, `overallRating`, and canonical ranking state. A future product decision can unify these only after migration semantics and Library grouping are reviewed. This avoids asserting that all current `experienced` entries were completed and lets current/paused items retain their real state.
6. **`entry_media_metadata` / selected normalized facts**: keep the user's selected format, language/region where meaningful, length value/unit/scope, and other supported facts separate from both `mediaTypeId` and source-native fields. Review conflicts before replacing selected values.
7. **Asset provenance**: for any cover copied from a remote catalog, persist provider/source ID, original URL, retrieval time, licence/attribution text and allowed retention/redistribution flags. Enforce provider-specific retention. If the provider does not permit local caching or redistribution in backups, do not turn the remote response into a content-addressed original asset. The user's local uploaded image pipeline can stay as-is.

Existing `EntryEvent` can record an import action (`source='import:<provider>'`) and imported activity/rating details after its contract is versioned. Keep an `ImportBatch` for batch-level undo; do not falsely label import time as original rating or watch date. `createdAt` remains the Tastellar creation instant. Imports must use the same revision/conflict rules as other writes and must not alter ranking placement without a user action.

## Identity, re-import, and undo

Use this deterministic matching order:

1. Exact `(provider, entity kind, external ID)` identity.
2. A saved user alias/link selected in a prior preview.
3. Suggested match using normalized title + release year + native format and a disambiguating creator/edition ID; require user confirmation.
4. Create a new work only after duplicate candidates are surfaced.

On re-import, update only opted-in fields. “Fill blanks only” remains the default; source changes to an already-populated field are previewed. Keep both native source status/rating and local state distinct. If a user edits a field after import, mark it locally changed so a later re-import cannot overwrite it silently. Deleting/renaming a provider connection does not remove library data. Re-importing the same export should be idempotent: exact identities update their source snapshot and create no duplicate work or duplicate history events.

Undo is a compensating action scoped to one batch, not database rollback. For new works, remove them only if they have not been subsequently edited, ranked, linked in a recap, or otherwise referenced; otherwise offer to keep and unlink the import identity. For updates, restore captured prior fields only if the version still matches the import result. If there is a conflict, offer field-by-field review. Never delete a manually added cover or user's review as part of a broad “undo import” without showing that field.

## Legal, provider terms, and privacy gates

Open source, noncommercial status, and optional voluntary donations do not automatically authorize scraping, API use, bulk copying, poster storage, or redistribution. Check provider API terms, website terms, copyright/ database rights, attribution, caching and deletion rules immediately before enabling each connector. Treat terms as capability gates in the provider registry. If terms are unclear or prohibit the product use, disable the provider and seek written permission; do not rely on “personal use” or noncommercial pricing alone.

Prefer a user's own official export over reading account pages. Never scrape HTML, bypass a login, collect credentials, defeat rate limits, proxy around an API, or fetch private lists on Tastellar's servers. For APIs, request least privilege, store secrets in the operating system keychain, keep list contents on-device, and disclose which fields are retained and where. Search catalog requests should disclose the provider receiving the query. Add provider attribution where required.

Treat covers as a separate rights decision from list import. Many catalog providers permit a thumbnail to be displayed under API terms but restrict permanent caching, offline use, export, or redistribution. Do not assume that a publicly viewable image is reusable. Prefer licensed image APIs, transient previews, and the user's own local cover file. Only persist a remote cover when the provider's written terms grant that exact use and the app preserves required attribution/retention behavior. Do not ship externally sourced covers in test fixtures or sample data without permission.

Avoid copying provider descriptions, plot summaries, critic/editorial reviews, or another user's reviews. User-authored reviews should be explicitly opt-in and remain local, but their inclusion must still follow export/API terms. A review authored by the importing user is not permission to collect other account data or redistribute the text. Store the minimum structured facts needed for identity and re-import, not a wholesale shadow copy of a provider database. Ask counsel to review provider terms and applicable copyright/database rights before public release; voluntary donations can affect the commercial characterization and should not be treated as a blanket exemption.

## Catalog search provider shortlist

Candidate search sources should be researched independently from import sources. A public catalog API is eligible only if its current terms allow Tastellar's use, its required credentials can be obtained legitimately, and its image policy supports the intended preview/persistence mode.

The supplied Letterboxd, IMDb, and Goodreads exports contain no cover URLs or artwork. Use their available identifiers only to find candidates, never as proof that an image is licensed: Letterboxd has only its canonical URI, so search by title/year; IMDb `Const` can resolve a TMDb candidate if enabled; a valid Goodreads ISBN can resolve an edition candidate, while Goodreads Book ID is not an Open Library ID. If ISBN is missing, search by title+author+publication year and let the user choose the edition. MAL title search is only for audiovisual entries and only against an approved catalog. Steam `appid` identifies a game, but owned-library access is conditional. In every case, show candidate title/type/year/creator and source attribution, let the user accept fields separately, and keep the cover transient unless explicit terms permit local retention. Candidate-data permission and artwork permission are independent gates.

- **Movies and TV:** TMDb is a candidate for title/year search and external IDs, but free use is restricted to non-commercial projects with attribution. The provider defines commercial use in revenue terms; because Tastellar may accept Boosty contributions, do not enable it without written provider determination/license. Do not assume Letterboxd or IMDb offers unrestricted public search APIs.
- **Anime/manga:** for MAL rows supplied by the user, title→TMDb candidate search is only for audiovisual rows and only after TMDb use is approved; do not use it for manga. Direct MAL HTML/account-page acquisition remains disabled pending permission. AniList is outside current scope and is not offered.
- **Games:** Steam Store/catalog search may be used only after reviewing Steam API/brand/image terms. IGDB is a candidate, but it requires Twitch credentials/server calls and routes commercial projects to partnership; resolve the donation/revenue classification with IGDB before enabling. Steam ownership data is a distinct user-authorized API import, not a catalog search result.
- **Books/comics:** Open Library and Google Books are candidates for ISBN/title search; verify each provider's cover policy, attribution, and request limits. Open Library discourages crawling/bulk downloads, and hosted cover URLs do not grant offline reuse rights. Goodreads is not a catalog API fallback; do not scrape it. Comic Vine's non-commercial/no-redistribution restrictions make it unsuitable as a default while donations are accepted unless it grants written permission.
- **Future user-list API:** Trakt is a strong later candidate for user-authorized history/ratings/list migration; its terms allow a one-off personal migration but prohibit scraping and catalog/community mirroring. It is an import source, not a reason to maintain a Trakt catalog copy.
- **General catalog:** avoid adding a catch-all metasearch or commercial metadata broker until its downstream data and image licences are clear.

Provider capability metadata should include: source type (export/API/catalog), supported media types, fields available, auth method, user-list permission, image preview permission, cache duration, attribution text, retention/deletion behavior, rate limits, and a last-reviewed date. A provider setup failure disables only that provider and leaves local manual entry/export paths usable. For detailed official-source evidence and donation/legal uncertainties, see [`import-provider-research.md`](import-provider-research.md); re-check all terms and approved use before public release or distribution.

## Delivery phases and acceptance gates

1. **Foundation — implemented:** versioned identity/import contracts, bounded staging, recognized-header file parsers, one reviewable multi-source preview, additive commit, import receipt, and conflict-safe batch undo. A generic arbitrary-column mapping UI remains future work.
2. **Initial sources — implemented in the current desktop flow:** Letterboxd ZIP, IMDb CSV, Goodreads CSV, MyAnimeList XML/XML.gz, one-title-per-line TXT and supported CSV/TSV, plus generic CSV/TSV with recognized fields. Steam owned-games import uses an explicit official API request with a saved user-supplied key and profile ID. AniList remains outside scope; wishlist/cart endpoints are not offered.
3. **Lifecycle UI:** add distinct status/progress display and controls for in-progress/paused/completed plus source-native format; decide how it coexists with existing Library groups and scores. Preserve legacy experienced values without silently converting them to completed.
4. **Catalog search — initial UI and provider adapters implemented:** TMDb, Open Library, Google Books, and IGDB searches are selected by the user and gated by provider capability/configuration. Keys are saved locally and are never returned by the status API. Search results and external IDs are explicit choices; remote cover references are separately opt-in and the exact current terms must be reviewed before distribution. Expand provider support only when rights and retention rules are clear.
5. **Broader providers:** consider Trakt for audiovisual lists and additional game/book databases only after official API permissions, export coverage, account-auth handling, and image rights are verified. Do not build arbitrary web scraping as a provider fallback. TMDb, IGDB, Comic Vine and any other non-commercial-only provider need a written determination on the Boosty arrangement before activation.

Acceptance should cover: same-file re-import idempotency; exact-ID and edition/season separation; title-collision preview; cross-provider conflicts staged together; existing-local-value precedence; all batch rating policies and row overrides; equal/unequal normalized ratings; comparable versus incomparable timestamps; unknown scales and zero sentinels; source-rating retention; dates mapped only to verified meanings; activity states/progress round-trip; unsupported/private rows; malformed and oversized files; parser version migration; cancellation before commit; transaction rollback; missing/unlicensed covers; token redaction; rate-limit/network failure; provider disablement after a terms change; and undo conflicts after a subsequent local edit. Preserve the inspected exports unchanged; run conflict, repeat-event, adaptation, invalid-date, invalid-ISBN, and tag-idempotency adversarial cases only against clearly labeled synthetic copies. The fixture analysis document contains those scenarios and observed counts. Add no test fixture containing personal credentials, real private lists, or unlicensed poster images.
