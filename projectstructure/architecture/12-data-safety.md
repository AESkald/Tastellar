# 12 — Data durability, archives, imports, migrations

Data protection is foundational, not a final-release enhancement. The complete offline library must remain accessible independently of payment, app account, or external service availability.

## Runtime storage and asset lifecycle

Use SQLite transactions, foreign keys, durable journaling appropriate to each host, and one writer. Verify schema version before writes. Store database and managed originals in an OS application-data location; never inside installation bundles. Covers and avatars are immutable content-addressed files with SHA-256 hashes. Derived thumbnails/palettes are rebuildable caches.

Asset import: validate supported type (initially PNG/JPEG/WebP), decode in a bounded background job, enforce 25 MB compressed and 40 megapixel decoded limits with a clear resize suggestion, strip unsafe metadata in display derivatives, hash, write temporary file, flush, rename into managed storage, then commit reference. Originals are preserved for portable export. A crash before reference commit leaves an orphan, not a dangling reference. Collect only assets unreferenced by active entries, trash, profile, recap snapshots, or retained backups, after a 7-day grace period. Never garbage-collect assets merely because no visible tab uses them.

Do not treat SVG/HTML as user image content in the initial pipeline. Missing or corrupt files produce placeholders and a repair report, never a database reset. Managed path resolution forbids escaping the asset root.

## Recovery and backups

Before every schema migration, create a consistent database backup with an asset manifest and hashes. Also offer automatic daily local snapshots when data changed: retain the newest 7 daily and 4 weekly snapshots by default, configurable. Default managed backups can share immutable assets; a user-exported portable archive is self-contained. Reference accounting must include managed backup manifests before collection. Failure of automatic backup displays status and retry; failure of mandatory pre-migration backup blocks migration and offers freeing space/export, not unsafe continuation.

Trash retention defaults to 30 days. Ordinary background cleanup must not silently permanently purge user records; at expiry mark items eligible and present a cleanup action/setting with explicit policy consent. Restore retains history and relations when possible. Purge explains that it removes entry text/history, duel evidence containing that entry, and its references from editable recap drafts (replace with empty slots); exported image files and existing backups are not retroactively erased. Immutable backups remain until explicit removal/retention expiry. Purge and orphan collection are separate operations.

## Full workspace reset

Reset is a deliberate permanent deletion, not a layout reset or a recoverable trash operation. Require an explicit confirmation that names the profile, Library and vocabulary, ratings and event history, trash, preferences, workspace, saved provider API credentials, managed images, and Tastellar-owned backups that will be removed. Clear all corresponding database rows and app-managed asset/backup files, increment the shared revision once, and repopulate only the current seeded defaults required for a blank install. Do not create a pre-reset recovery copy; that would retain data the user explicitly asked to delete. Separately exported archives outside Tastellar's managed data directory are unaffected. Complete the persistent reset before clearing in-memory Home, Library, provider credentials, avatar, cover, workspace, and per-tab view state so stale hydration cannot write deleted data back.

Reset filesystem changes use a durable journal containing the expected database revision and hard-link recovery snapshots of managed assets and backups. Write and sync the journal before renaming managed directories; retain recovery snapshots until the database transaction outcome is known. On pre-commit failure, restore the prior managed directories. After commit, enable SQLite secure deletion, require a successful WAL truncate checkpoint, vacuum the database, then require a second successful WAL truncate before deleting recovery snapshots and the journal. At startup, compare the saved revision with the journal: an unchanged revision means roll back the filesystem changes, and the single incremented revision means finish the committed reset cleanup. Recovery and cleanup are idempotent. If database scrubbing, file cleanup, or journal removal fails after commit, return a distinct `ResetCommittedCleanupPending` outcome: the reset succeeded, so rehydrate the blank state and show a localized warning that secure cleanup remains pending; never report that the reset failed or restore deleted user data.

## Ranking-only reset

Ranking reset is a separate, confirmed action in **Settings → Data & privacy**. It clears only the active library's media-ranking state: placement assignments, duel and placement-assist sessions, direct judgments and retractions, skips, manual boundary factors, fitted model state, reconciliation records, and ranking OrderEvents. Set every rated entry to `rankingPlaced=false` and move it into its tier's Unplaced tray while preserving its relative order there. Preserve every entry and its content, 1–10 overall ratings and rating history, criteria scores, reviews, tags, media types, assets, trash, unscored-group state/order, Home, preferences, workspace, and all unrelated EntryEvents. Do not delete or rewrite managed backups or separately exported archives; confirmation copy must say that restoring an existing backup/archive may restore its ranking history.

Require the current shared library revision and perform the database mutation atomically, incrementing that revision once. A stale revision or failed transaction leaves current placement/evidence unchanged. On success, refresh Library, Ranking, Analytics, and other order readers against the returned revision; do not clear Home, settings, workspace, assets, or per-tab state as the full workspace reset does. No ranking-only reset recovery copy is created. Migration initializes pre-feature rated entries as placed in their prior order; newly rated entries start unplaced. See [the ranking specification](../specifications/09-ranking.md).

On corruption: stop writes, preserve originals, open a recovery view with diagnostics, newest verified backup choices, and export of readable records where possible. Never create an empty library over damaged data. Restoring a backup requires preview and a backup of the current state if readable.

## Portable archive versions 1 through 4

The desktop app uses the `.tastellar.json` extension and a single UTF-8 JSON document. It is not a ZIP file. The document contains the versioned `tastellar-library` manifest, `home`, `library`, `history`, `assets`, and `readme` fields. Version 4 adds `providerCredentials` and a manifest entry for virtual `data/provider-credentials.json`; versions 1–3 do not contain that field or path. Every descriptor carries a byte size and SHA-256 hash. Referenced original images, including profile avatars and active or trashed story covers, are embedded as base64. The archive is portable and inspectable and does not use proprietary encryption.

Provider keys entered from Add work or Import API settings are stored locally in the SQLite `provider_credential` table. They are kept out of the application binary and are never returned through the capability API. Version 4 archives include those keys as plain text in the `providerCredentials` section and verify that section with the manifest descriptor. Treat exported archives as sensitive. Versions 1–3 remain importable and replace the destination's provider credentials with an empty set.

Version 1 contains profile, rating guidelines, taste inputs, preferences and workspace, stories, media types and their icon keys, criteria and their type assignments, tags, criterion scores and their recorded timestamps, active and trashed records, entry events, group ordering, and referenced image originals. Stable IDs, record versions and timestamps, archived vocabulary, partial dates, and trash metadata are preserved. It has no ranking state. Legacy entry `notesText` is intentionally discarded during migration/import; it is never copied into the review field.

Version 2 adds ranking placements and unplaced tray order, ordinary and placement-assist sessions with frozen snapshots, exact participant IDs, explicit-subset flags and seeds, every judgment including ties and skips plus retractions, manual boundary factors and their unlock-judgment references, each tier's E, C and `pendingReconcile`, OrderEvents, and `orderKeyAlgorithmVersion`. The nested ranking payload is schema version 3 and records per-tier judgment input sequences and boundary creation sequences. Nested ranking schema versions 1 and 2 lack chronology; import preserves their unlocked state with a legacy marker and clears unproven unlock links. Validate each v3 unlock reference against an active opposing win for the same pair and tier with a judgment sequence greater than the boundary creation sequence. Rebuildable fitted posterior and covariance caches are omitted. Validate references and ranking state before replacing the destination: active binary/confirmation snapshots, candidate membership, bounds and presented pivots must match the restored placed order; active manual factors must be unique by unordered pair; and `C ≤ E` (reject `C > E`). Preserve `pendingReconcile` independently of C: dirty manual or membership-only state may have false, while a fit-clean tier may have true if reconciliation was interrupted. An active placement assist must have `pendingReconcile=false`.

Continue accepting version 1 archives. Since they have no key-version field, interpret their keys with algorithm 1, sort each group with that ordering, then re-encode the keys under current algorithm 2 while preserving the entry sequence. Mark their rated entries placed and initialize ranking evidence empty. Version 2 archives carry the key version; recognized older keys are re-encoded the same way, while current-version keys retain their exact values. The SQLite migrations create mandatory pre-migration backups before changing ranking tables. Import validates and commits placement, canonical order, E, C and `pendingReconcile` together; it does not reconcile inside that transaction. After commit or restart, refit whenever C < E and reconcile only when `pendingReconcile=true`. An active placement assist resumes only against its frozen snapshot and matching revisions; otherwise preserve its answers and leave its target unplaced. Until queued work succeeds, stale or failed jobs must not overwrite the imported order.

Current automatic limits are 512 MiB for the JSON archive, 256 MiB for the total described file content, 128 MiB per state/history file, and 25 MiB per image. JSON nesting is limited to 20 levels. The implementation validates manifest paths, duplicate paths, file sizes, hashes, image content and entity references before restoring. A successful import replaces Home and Library together in one database transaction. It first writes a complete pre-import archive; there is no Merge mode or import preview yet. Export writes a temporary file in the destination directory and only reports success after finalizing it. These limits and format details must be reflected in the UI and README; broader volume limits, ZIP containers, merge behavior, schemas, and sample archives remain follow-up work.

## Export consistency

Read a consistent database snapshot at revision R, collect all referenced immutable assets, pin them against collection, write archive to a temporary destination, hash/verify, then atomically finalize where the OS supports it. Otherwise write a distinct completed file and report only after full verification. Library edits after R are not partly mixed into that archive. Insufficient space/cancellation leaves the previous valid export intact. Output includes a report of missing assets; default export blocks on missing referenced originals and offers an explicitly labeled partial archive only with user choice.

## Import pipeline

1. Select a `.tastellar.json` file; validate format version, nesting, manifest paths, hashes, counts, provider names and credential payloads, images, schema, entity constraints, references, dates, order keys, and supported sizes before touching active data. Migrate recognized older schemas, including discarding legacy `notesText` and reconciling only seeded default vocabulary; preserve user-created vocabulary. Versions 1–3 contain no provider credentials, so replacing from one clears existing keys. Reject absolute/traversal paths, duplicate paths, malformed input, excessive records, and damaged assets. Do not allocate based on untrusted declared sizes.
2. Stage and validate all referenced images, then write a full pre-import archive before mutation. Missing or corrupt required data blocks import.
3. Ask for explicit confirmation to **Replace library**. Import preview and Merge are follow-up work; until then, the Settings and Library entry points must clearly warn that the current profile and library will be replaced.
4. Stage assets first; commit Home, Library, and provider credentials together in one transaction and increment the shared library revision once. A failed commit leaves active database state intact; staged immutable assets can be collected as orphans.
5. Refresh Home and Library queries after successful restore. Current-schema fields are preserved; the documented legacy `notesText` and seeded-vocabulary reconciliation are explicit migration rules. Other unknown fields and newer archive versions are rejected before mutation.

The current portable workspace settings use the existing Home model. As additional models are introduced, extend the archive format deliberately and preserve the same validation, atomic replacement, and recovery guarantees. Merge history, conflict resolution, import provenance, and cross-platform workspace mapping remain future work.

## Migration/update contract

Sequential numbered migrations, transactional where SQLite permits, with representative fixtures for every supported schema. Test upgrade directly from every supported released version through the full chain. Large asset transformations use restartable staged jobs and completion markers. Validate post-migration foreign keys, constraints, counts and representative asset hashes. Failure retains the old database/backup and enters recovery; never continue partially migrated. Older binaries reject newer schema in read-only recovery mode rather than downgrading destructively. App rollback restores a matching backup only with explanation/consent.

## Acceptance

Archive verification covers full round trip of profile/avatar, entry fields and ratings, tags and vocabulary, entry history and ordering, trash metadata, and original asset hashes; invalid archives must leave active data unchanged. Add fault injection for disk full, process termination at each import/export/migration stage, corrupt images, missing assets, duplicate IDs, malicious manifest paths, unsupported versions, and interrupted writes. As later domain models ship, extend round-trip coverage to their history and references. Data loss must never be disguised as successful startup.
